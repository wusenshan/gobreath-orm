## v0.1.16 (2026-11-12)

- **feat: The `Remove` family — physically delete rows with row-level auditing (penetrating soft delete)**: physical deletes used to be `ForceDelete*` only, and that is a **blind delete**: one `DELETE` goes out and the caller receives nothing but `RowsAffected` — **there is no record of which rows were destroyed**. Compliance hard-delete, data purging, and data-repair scenarios all require "keep a record before deleting", which previously meant selecting first and deleting one by one yourself (two hand-assembled steps whose conditions could drift apart). Three first-class entry points are now provided (`remove.go`, plus `repo.go` wrappers):
  - `Remove(ctx, db, entities ...*T)`: one or many entities, deleted by primary key;
  - `RemoveQuery(ctx, db, q)`: by query condition, returning the deleted-row snapshot;
  - `RemoveSQL[T](ctx, db, sql, args...)`: a custom `SELECT` defines the scope (**SELECT only**; arbitrary `DELETE` still goes through `RawExec`, and the semantic difference is stated in both the docs and the error message).

  The shared flow is **`SELECT` a full row snapshot first (penetrating soft delete — no "not deleted" condition, so already soft-deleted rows are included) → `DELETE` by the captured primary keys in chunks → emit a `RemoveEvent` per chunk**. Key design points: ① **the rows a hook sees are exactly the rows deleted** — deletion is by captured primary key rather than re-using the original condition, eliminating the window where rows change between "condition matched" and "`DELETE` issued"; ② `RemoveEvent{Table, SQL, Args, Count, Rows, PKs}` carries both the row snapshot (dynamic type `[]*T`) and normalised primary keys (`keyOf` semantics, so logging needs no reflection); listeners register via `Config.RemoveListeners` / `db.WithRemoveListener`, with a ready-made `RemoveAuditLogger(w)`; ③ chunk size is capped at `removeInChunk = 500` (matching the `preloadInChunk` parameter-limit rationale) with **an independent event per chunk**; ④ every guard runs **before any `DELETE` is issued**: zero primary key (a classic sign of a badly assembled entity), empty entity list (`ErrInvalidArgument`), an unbounded `RemoveQuery`, a `RemoveQuery` with `Limit`/`Offset` ("delete the first N" silently degrading means a full-table physical delete), a `RemoveSQL` whose leading SELECT table does not match the entity (validated only when a table name can be extracted, so nothing is falsely blocked), and a SELECT projection missing the primary key; ⑤ every derived DB inherits the listeners (all 8 copy constructors — `WithPrefix` / `WithLogger` / `WithExecutor`, etc. — are wired) because losing listeners on a derived DB means auditing silently stops. Documented boundaries: capture and delete **do not open an implicit transaction** (wrap in `db.Transaction` for strict consistency), and this sits at a different layer from the existing `Hook` (`HookKindExec`, which only sees SQL text). Added `remove_test.go` (SQL shape / arguments / event contents / soft-delete penetration / chunking / five guard classes / derived inheritance / Repo forwarding) and the real-database `integration/remove_it_test.go` (passing on SQLite: soft-deleted rows are physically removed and invisible even to Unscoped, multi-entity single batch, conditional delete snapshot, `RemoveSQL` including soft-deleted rows, guards leaving zero trace); **4 mutation checks all turn red** (drop the zero-PK guard, drop the leading-table validation, drop the `Limit` guard, drop listeners in `WithPrefix`).

- **feat (breaking): `OnlyColumns` whitelist unified on the type-safe `ColExpr` form**: the `OnlyColumns(cols ...string)` released in v0.1.13 still took hand-written string column names, contradicting the builder's "zero field names / zero SQL strings at the call site" principle — a renamed field would not follow, and a typo only surfaced at `filterOnlyCols` during execution. The signature is now `OnlyColumns(cols ...ColExpr)`: columns come from `orm.Col[T](closure)` / `orm.ColOf[T](fieldName)` / generator-produced `XxxCols.Field`, structurally identical to `Eq` / `OrderBy`, so a renamed field is a compile error and the column name always comes from the `db` tag. Dynamic column names (from configuration or variables) use the new string escape hatch `OnlyColumnsRaw(cols ...string)`, which the framework still validates before execution (typos / primary key / auto-increment / logical-delete columns are reported as before, never silently ignored). The write side (`filterOnlyCols` and its validation) is unchanged — `writeConfig.only` stays `[]string`, populated from `ColExpr.Name()` at construction. Migration: `OnlyColumns("title")` → `OnlyColumns(orm.Col[Article](func(a *Article) *string { return &a.Title }))` or `OnlyColumns(ArticleCols.Title)`; use `OnlyColumnsRaw` when strings are genuinely required. (`crud.go` + `only_columns_test.go` + `integration/api_it_test.go` + README examples updated.)

## v0.1.15 (2026-10-25)

- **fix (breaking): the `Distinct()` + vector-search gate left a back door open for `Count` / `Page` / aggregates — the SQL generated there was invalid**: the v0.1.13 gate was written as `q.distinct && q.hasVector && !noVecCol`, on the theory that "Count's inner query sets `noVecCol=true`, carries no dist column, so de-duplication is not defeated and it can stay allowed". **That reasoning was wrong**: `noVecCol` only suppresses the dist column in the projection, while distance ordering is still produced from `hasVector`, so the inner query really builds `SELECT DISTINCT * FROM "articles" ORDER BY "emb" <-> $1 LIMIT 3`. Measured against real databases the three dialects differ: **PostgreSQL always rejects** with `for SELECT DISTINCT, ORDER BY expressions must appear in select list`; **MySQL reports 3065 only when the sort column is not in the projection** (with the default `DISTINCT *` projection it accepts); **SQLite accepts it and runs silently**. The same query therefore "explodes on PG, passes on MySQL/SQLite", and no cross-dialect contract can be maintained; combined with the contract gap where `SelectList` already panics but `Count` was allowed, callers using `Page` would only ever get a database syntax error without a stack trace. The gate now drops `!noVecCol`, so `SelectList` / `Count` / `Page` / `Sum` and other aggregates **all panic**. Dropping the `ORDER BY` is not a workaround: once nearest-neighbour ordering disappears, `LIMIT k` truncates an arbitrary k rows and `Count` silently reports a meaningless number. The old `TestCountStillAllowsDistinctWithVector` (which only asserted "no dist column in the SQL" and never checked `ORDER BY` — a false green) was rewritten as `TestCountRejectsDistinctWithVector` (Count / Page / Sum sub-cases); **mutation check**: reverting the gate to `&& !noVecCol` turns the Count and Sum sub-cases red.
- **fix: `UpdateByIdSets` (single row) still emitted `SET` columns in random order — the v0.1.13 "fixed" note only covered two entries**: `updateSetsImpl` and the batch `UpdateByIdsSets` both applied `sort.Strings(cols)`, yet single-row `UpdateByIdSets` still did `for col, val := range sets`. The same `sets` produced different SQL text each run → prepared-statement cache hit rate collapses, and slow-query logs and byte-exact assertions become unstable. It now iterates after sorting by column name, matching the other three entries. Added `TestUpdateByIdSetsColumnOrderDeterministic` (30 rounds of byte-exact comparison plus lexicographic position assertions); **mutation check**: removing that `sort.Strings` turns the case red.
- **fix: introspection APIs accepted unvalidated table names (the safety assumption lived only in a comment)**: `DescribeTable` / `TableExists` / `ColumnExists` accepted any `table string` and passed it down to `sqlLiteral` (which only doubles single quotes), while the comment on `tableColumnsDetailSQL` claimed "the table name has passed `quoteTable` validation" — true only on the `AutoMigrate` path (where the name comes from `meta.finalTable()`). Public API table names come straight from the caller and never pass `identRe`. MySQL does not enable `NO_BACKSLASH_ESCAPES` by default, so a backslash is an escape character: a table name ending in a backslash leaves the literal unterminated and rewrites the surrounding SQL structure. All three entries now go through `validateTableName` (the same `identRe` whitelist as `quoteTable`, supporting two-part `schema.table`), returning `ErrInvalidArgument` rather than panicking — this is runtime input, not a programming-time error. Added `TestIntrospectionRejectsInvalidTableName` (9 invalid forms plus a reverse assertion for the legal `users` / `public.users` so normal usage is not broken); **mutation check**: removing the three call sites turns the case red.
- **fix (breaking): `WithinDistance` used alone silently appended a `dist` column and sorted by distance — callers who only wanted a threshold filter paid for a full-table distance computation plus a sort**: `WithinDistance` only set `hasVector` / `vecFilterOn`, appending neither an `order{vec:true}` entry nor `noVecCol`, so both fallback branches in `Build()` fired — `if q.hasVector && !noVecCol` appended `distance AS dist`, and `else if q.hasVector && q.aggFn == ""` (with empty `orders`) added `ORDER BY distance`. Measured SQL: `SELECT *, "embedding" <-> $1 AS dist FROM "zz_docs" WHERE "embedding" <-> $1 < $2 ORDER BY "embedding" <-> $1`. All three costs are silent: ① without a vector index this is a full-table distance computation plus sort, when the caller only wanted filtering; ② the result set gains a `dist` column out of nowhere (entity mapping ignores `fields[i] == -1`, and `Aggregate[DTO]` / `RawQuery` into DTOs also ignore the extra column rather than misaligning — the real problem is the wasted distance expression); ③ it was the underlying cause of the blanket `Distinct()` + vector panic in v0.1.13: with both the sort and the projection removed, `SELECT DISTINCT * FROM t WHERE distance < ?` is perfectly legal, and "how many rows in the neighbourhood after de-duplication" ought to be computable. A new `vecOrder bool` (set only by `Nearest` / `NearestBy`) now drives both the `dist` projection and the `ORDER BY` fallback, and the `Distinct` gate keys off `vecOrder` instead of `hasVector`. **Behaviour change**: using `WithinDistance` alone no longer sorts by distance and no longer adds a `dist` column — chain `Nearest` explicitly if you need ordering. Added `TestWithinDistanceIsFilterOnly` (three dialects: assert no `AS dist`, no `ORDER BY`, and exactly "vector + threshold" arguments) / `TestNearestStillProjectsAndOrders` (the narrowing did not break nearest-neighbour retrieval) / `TestDistinctAllowsVectorThreshold` (including an assertion that `countBuild`'s inner query keeps DISTINCT) / `TestDistinctWithNearestStillPanics` (message changed to "order by distance"), plus a real-database section in `vectorDistanceChecks` for `Distinct + WithinDistance + Count` — PG reports `for SELECT DISTINCT, ORDER BY expressions must appear in select list` the moment a distance `ORDER BY` survives, so **passing proves the ordering is gone** (4 backends: sqlite / mysql 8.0.30 without vector support skips automatically; both pgx and lib/pq paths pass).
- **feat: `UpdateByIds` — update a batch of entities by primary key row by row**: previously batch-by-primary-key meant only `UpdateByIdsSets` (one `sets` applied to many rows), so per-row values required a hand-written `for` loop. A first-class entry is now available (`crud.go` plus a `repo.go` wrapper). The semantics stay deliberately plain with the cost written into the docs: ① **executed row by row** — each row has different `SET` values, and merging would require `CASE WHEN` or value grouping, growing the SQL with row count and hitting parameter limits; do not compare its throughput with `BatchInsert`; ② **no implicit transaction** — on a mid-way failure, earlier rows are not rolled back; wrap in `db.Transaction` for atomicity (the docs include an example); ③ **stops at the first error**, with the index and primary-key value in the message (`row 0 (id = 7) update failed: ...`), preserving the error chain via `%w` so `errors.Is(err, ErrOptimisticLock)` still works; ④ **a zero primary key is a hard error** — batch update never inserts, and a zero key usually indicates a mis-assembled entity (missed scan / key lost in a copy); silently skipping is far more dangerous than failing; ⑤ an empty slice returns `nil` (a no-op, not an error — unlike `DeleteByIds`, where an empty ID list is rejected because folding it into an empty condition means a full-table operation); ⑥ with an optimistic-lock version column, versions are compared and incremented per row, matching `UpdateById`. Added `update_by_ids_test.go` (a driver whose `RowsAffected` is configurable: two UPDATEs executed row by row with positionally matching arguments, zero statements for an empty slice, a zero key rejected at row 1 with only one statement executed, zero statements for a model without a primary key, the optimistic-lock error chain, Repo forwarding) plus real-database `TestUpdateByIdsOnRealDB` (4 backends: both rows changed, unlisted rows untouched, zero key reported with its row number) / `TestUpdateByIdsOptimisticLockOnRealDB` (4 backends: after rolling the version back one step, row 0 conflicts and **row 1 really was not executed** — the real database is the only gate for "stop on first error", since a mock can only observe call counts).
- **feat: `SelectCountDistinct` — grouped distinct counting via `COUNT(DISTINCT col)`**: `selItem`'s aggregate whitelist only had `COUNT(*)` (`SelectCount`), which cannot express a very common statistic like "how many distinct customers per department" — `Distinct()` applies to whole rows and is a different thing, and using it overcounts. `selItem` now carries `distinct bool` and renders `FN(DISTINCT col)`, with a matching `SelectCountDistinct(col ColExpr, alias string)`; aliases still go through `appendAgg`'s mandatory check (dialects name anonymous aggregate columns differently, so DTO mapping would silently miss). Per SQL semantics `COUNT(DISTINCT col)` **excludes NULL**, and the docs state this ("use `GroupBy` if you need the NULL group counted separately"). Added `TestSelectCountDistinctBuildsSQL` (byte-exact for three dialects) / `TestSelectCountDistinctRequiresAlias` / `TestSelectCountDistinctIsNotSelectDistinct` (asserts `DISTINCT` sits inside the parentheses and never leaks into `SELECT DISTINCT`), plus real-database `TestSelectCountDistinctOnRealDB` (4 backends, data `a:alice,alice,bob` + `b:carol`, expecting a=2 / b=1 — **whole-row distinct would report 3**, and that number is precisely the discriminator for "did it really de-duplicate per column").
- **fix: on models with an optimistic-lock version column, `Save`'s promised `ErrNotFound` was unreachable**: `updateByIdImpl`'s WHERE carries both the primary key and `version = old value`, so on zero affected rows it always returns `ErrOptimisticLock` (that layer genuinely cannot distinguish "row does not exist" from "version changed underneath"), while `Save`'s `n == 0 → ErrNotFound` branch sits after `err == nil` — unreachable for versioned models, so `errors.Is(err, ErrNotFound)` missed the "row does not exist" case. `Save` no longer pretends to distinguish: with a version column it wraps an explanation that "**the row does not exist / was logically deleted / the version conflicted** — one of the three, indistinguishable from affected-row count alone; use `SelectById` first if you need certainty before retrying", still wrapping `ErrOptimisticLock` via `%w` (it deliberately does **not** also satisfy `ErrNotFound`, otherwise a version conflict would be misreported as a missing row). The no-version path and its error text are unchanged. Added `save_semantics_test.go`: `TestSaveZeroRowsNoVersionIsNotFound` / `TestSaveZeroRowsWithVersionIsOptimisticLock` (including "must not also satisfy ErrNotFound" and assertions on four key message fragments).
- **fix: with read/write splitting configured, the primary opened two connection pools — pool settings, `db.SQL()`, and `Close()` all landed on the wrong one**: `Open` first opened pool A on `cfg.DSN` and attached it to `db.exec`, then `newReadWriteRouter` unconditionally opened pool B from the same DSN for `router.primary`, with no reuse check. Ordinary queries (`execContext` / `queryContext` / `queryRowContext`), `queryPrimaryContext`, and all CRUD go through the router, leaving pool A used only by `Transaction` and `db.SQL()`. Four consequences, all silent: ① `MaxOpenConns` / `MaxIdleConns` / `ConnMaxLifetime` / `ConnMaxIdleTime` were applied only to the pool that barely serves queries — rate-limiting the primary limited the wrong object, while the primary's connection count was really A + B; ② `db.SQL()` returned pool A, so `Stats()` QPS / connection counts stayed near zero (dashboards looked idle), runtime `SetMaxOpenConns` had no effect on the query path, and `Ping` checked the other pool; ③ `db.SQL().Close()` could not close the router's primary or the replica pools, so graceful shutdown leaked connections; ④ when `newReadWriteRouter` returned an error, pool A was orphaned (repeated in-process retries would exhaust handles). The primary is now owned by the router, with `db.exec` and `router.primary` pointing at **the same pool**: when `Primary` shares the source of `cfg.Driver`/`DSN` (the most common setup) the already-open pool is reused, and when it differs, `Primary` wins (previously `Transaction` opened on `cfg.DSN` while ordinary queries went to `Primary` — two different databases). Pool settings were extracted into `applyPoolSettings`, applied to the primary and **each replica** (replica pools previously fell back to `database/sql`'s default "no limit"). New `DB.Close()` closes the primary and every replica pool in one call (`*sql.DB` de-duplicated, non-`*sql.DB` skipped, `*sql.DB.Close` idempotent), including pools opened on error paths. Added `open_pool_test.go`: primary pool pointer identity / pool settings landing on the primary and two replicas / `db.SQL() == router.primary` when the primary is a different source / all three pools failing `Ping` after `Close` with repeated `Close` safe / behaviour unchanged without routing / `Open` erroring when a replica cannot be opened; **4 mutation checks all turn red** (open a second pool on the same source, skip pool settings on the same source, skip pool settings for replicas, skip replicas in `Close`). **Observable behaviour change**: under read/write splitting, `db.SQL()` now returns a different pool (the one queries actually use), so code relying on it for runtime tuning or statistics will see real numbers.
- **docs: documented that `UpdateByIds` "succeeds silently when a row does not exist"**: a zero primary key is an error (mis-assembled entity), while a non-zero key whose row was concurrently deleted follows `UpdateById` semantics — `nil` without a version column, `ErrOptimisticLock` with one. The asymmetry is intentional: the latter is a normal outcome of a batch update. The docs state this and point at `Save` ("treat missing as failure") for the opposite contract. Also corrected the stale comment on `setterFor` (it now branches `,vector` / JSON columns first, then specialises scalars).
- **fix (breaking): `UpdateSets` / `UpdatePartial` could write the optimistic-lock version column to any value — silently disabling conflict detection**: `resolveVersion` was wired into four entries (`updateByIdImpl` / `Update` / `UpdateByIdSets` / `UpdateByIdsSets`) but not into their shared core `updateSetsImpl`, which only ran `checkSetCols`, and `checkSetCols` only blocks `nil` / `ignore` / `pk`. So `UpdatePartial(ctx, db, q, map[string]any{"status": "paid", "version": 999})` (the common pattern of binding an entire HTTP body into a map) generated `UPDATE ... SET "status" = $1, "version" = $2` — **no `WHERE version = ?`, no increment, no error**, flattening the version of every matched row, after which other sessions holding the real version could never match again. This is the same class of reasoning that already blocked the primary key in `checkSetCols` (changing the key orphans related data; changing the version orphans concurrency detection) — only the former was blocked. A `sets` map containing the version column now returns `ErrInvalidArgument` pointing at the alternative entries. **The check was deliberately not put inside `checkSetCols`**: `UpdateByIdSets` relies on `sets` carrying a version value to trigger single-row optimistic locking (legitimate there), so a blanket rejection would kill that path. The existing rule "map entries do not bump the version column" is now documented (same origin as `UpdateByIdSets` not touching the version column when `sets` omits it) — use the entity path `Update` for conditional batch updates that should increment versions (`version = version + 1`). Added `review_round3_test.go`: `TestUpdateSetsRejectsVersionColumn` (two entries × `errors.Is(ErrInvalidArgument)` × message containing "version" × **no SQL issued**) / `TestUpdateSetsWithoutVersionStillWorks` (reverse assertion, no collateral damage); **mutation check**: removing the guard turns both sub-cases red.
- **fix (breaking): `Upsert` / `BatchUpsert` never validated `conflictCols`, and on MySQL a typo was silent**: `conflictCols` flowed straight into `dialect.UpsertSuffix` with no check that the column exists on the model and no rejection of empty strings or duplicates. This is not injection (it goes through `QuoteIdent`), but it contradicts `checkSetCols`' contract for map entries and, worse, **behaves oppositely across dialects**: PG / SQLite splice the conflict key verbatim into `ON CONFLICT (...)`, so a typo is reported by the database (`column "emial" does not exist`, without pointing back to the call site) and duplicates fail with `conflict target specified more than once`; **MySQL's `ON DUPLICATE KEY UPDATE` syntax has no slot for a conflict key at all and ignores `conflictCols` completely**, always deciding on the table's existing unique indexes — the same typo produces no error on MySQL and silently inserts or updates against a different unique key while the caller believes it specified one. Added `checkConflictCols` (shared by `Upsert` / `BatchUpsert`): empty strings / duplicates / columns absent from the model all return `ErrInvalidArgument` without issuing SQL. Only `fi == nil` is rejected; columns tagged `,ignore` are allowed (the column really exists, the ORM just does not write it — using it as a conflict key is legitimate). **The boundary is documented**: on MySQL, "the conflict key is correct" still does not mean it takes effect; the table's unique indexes are what decide. For conflict resolution on unmapped columns, use raw SQL. Added `TestUpsertRejectsInvalidConflictCols` (two entries × three invalid forms, asserting error type, message fragments, and zero SQL) / `TestUpsertAcceptsValidConflictCol` (PG suffix shape) / `TestUpsertMySQLIgnoresConflictColsRealButSilent` (pins the current "MySQL SQL contains no conflict key" behaviour so nobody later assumes otherwise); **mutation check**: removing either call site turns the corresponding sub-case red.
- **docs: two cases of "behaviour in the code, absent from the docs" filled in**: ① `Aggregate[DTO]` NULL semantics — when grouped results are scanned into a DTO, `NULL` reaching a non-pointer field is a **silent zero value** (`prepareTarget` keeps the zero value when `val == nil`), so a `float64` field cannot distinguish "the group sums to 0" from "the group is all NULL"; declare the DTO field as `*float64` to distinguish them (the pointer is set to nil), now documented in the README (verified against a real database and unit tests: NULL → `float64` gives 0, → `*float64` gives nil). ② `AutoMigrate` creates vector **columns** but not vector indexes, and `VECTOR.md` now explains why: PG's HNSW index must bind the ops matching the metric (`vector_cosine_ops` / `vector_l2_ops` / `vector_ip_ops`), while **the metric is a query-time parameter** (`NearestBy(..., Cosine)`), so the model layer cannot know which to build; MySQL community editions have no `VECTOR INDEX` (HeatWave / MySQL AI only), and SQLite has no vector support at all — auto-creating would only manufacture the illusion of an index that never gets used. Hand-written index scripts for all three dialects were already in `VECTOR.md` §4.3, the README, and `examples`.

## v0.1.14 (2026-10-22)

- **feat: first-class batch-by-primary-key APIs (`SelectByIds` / `DeleteByIds` / `ForceDeleteByIds` / `UpdateByIdsSets`)**: the most common service-layer "query / delete / update by ID list" operations previously required assembling `In()` by hand; there are now first-class entries (`crud.go` plus `repo.go` wrappers). Semantics: ① **an empty ID list returns `ErrInvalidArgument`** (a new shared error) — `IN ()` is not valid SQL, and folding it into an always-true condition equals a full-table read/delete, so a call that is almost certainly a missing parameter must fail loudly instead of silently scanning the table; ② delete entries share the singular semantics (logical delete when an active logic column exists, physical otherwise) and return affected rows; ③ the soft-delete branch strictly obeys "SET arguments allocated before WHERE" — the batch form hits positional-dialect argument misalignment too (on MySQL / SQLite the delete value gets bound to the condition column → silently 0 rows), and string assertions on mocks cannot tell `?` occurrences apart (verified by mutation: shifting the `idsIN` start index turned **only the PG sub-case red**, because `$n` carries ordinals; MySQL / SQLite still passed), so **a real database is the only gate** (`integration/batch_apis_it_test.go` inserts 4 rows, deletes 3, 1 remains; 4 backends green); ④ `UpdateByIdsSets` keeps the single-row difference: **the batch form does not support optimistic locking** — target rows have different versions and a single `WHERE version = old` cannot express that, so a version column in `sets` is a hard error rather than silently emitting a condition that only holds for some rows; `SET` columns are sorted by name (same reasoning as `updateSetsImpl`). Added `batch_apis_test.go` (byte-and-position assertions for three dialects plus guards) and three real-database cases (`TestBatchByIDApisOnRealDB` / `TestBatchByIDSoftDeleteArgOrderOnRealDB` / `TestDescribeTableOnRealDB`, 4 backends).
- **feat: `Save` — the "intuitive" insert-or-update-by-primary-key entry**: a zero primary key (including a nil pointer) → `Insert` (auto-increment write-back as usual); non-zero → full-column update per `UpdateById`, **returning `ErrNotFound` when 0 rows are affected (row missing or logically deleted)** — neither silent nor falling back to Insert: holding a non-zero key and inserting a new row usually means the key was accidentally cleared or the row concurrently deleted, which should fail loudly (use `Upsert` for real upsert semantics). To support this, `UpdateById`'s core was extracted into `updateByIdImpl` (returning affected rows); `UpdateById` behaviour is unchanged. The only tightened contract is that an error from `RowsAffected` no longer silently skips the row-count check and reports success (all three major dialects report `RowsAffected` reliably, so the practical impact is nil).
- **feat: schema introspection (`TableExists` / `ColumnExists` / `DescribeTable`)**: returns `[]ColumnMeta{ Name, DataType, Nullable, Default, PrimaryKey, AutoIncrement }`, serving dynamic table creation, migration checks, and export auditing (`schema.go`). The three dialects produce **structurally identical 6 columns** consumed by a single scan function: PG uses `information_schema.columns` plus a primary-key `EXISTS` subquery and dual `is_identity`/`nextval` detection (covering both `serial` and identity forms); MySQL uses `column_key='PRI'` plus `extra LIKE '%auto_increment%'`; SQLite reshapes `pragma_table_info`. Design points: ① introspection issues a SELECT but always goes **to the primary** (reusing AutoMigrate's `queryPrimaryContext` routing) — replica DDL may lag, and inspecting structure there yields conclusions opposite to reality; ② when a dialect does not support introspection (a custom dialect without `DialectKinder`), it **returns an error rather than false** — letting "I don't know" masquerade as "it doesn't exist" makes callers recreate tables; ③ `TableExists` / `ColumnExists` reuse AutoMigrate's existing column introspection (same case normalisation) rather than growing a second query path. **A dialect trap was caught on a real database**: SQLite's `pragma_table_info` output columns `notnull` / `pk` / `cid` must be quoted (`"notnull"`); unquoted, the lexer splits it into `NOT NULL` tokens and reports `near "notnull": syntax error` — AutoMigrate's old query only did `SELECT name`, which is why it never hit this. Five spellings were probed before settling on quoting every column. AutoMigrate's introspection error text was neutralised at the same time (it used to mention "AutoMigrate", which would mislead debugging once public APIs reuse it).
- **test: four real-database backends all green** (sqlite + postgres/pgx + postgres-libpq + mysql): `TestBatchByIDApisOnRealDB` (batch select/update/delete + ForceDelete + three `Save` branches + error on a non-existent key), `TestBatchByIDSoftDeleteArgOrderOnRealDB` (soft-delete batch argument order — indistinguishable on mocks for positional dialects, so this is the only gate), `TestDescribeTableOnRealDB` (after AutoMigrate: column list / primary key / auto-increment / nullability introspection plus `TableExists` / `ColumnExists` case normalisation).
- **feat: streaming iteration `QueryIter` (large-table scans without loading into memory)**: a single cursor yielding rows as `iter.Seq2[*T, error]` (`iter.go`, Go 1.23's `iter` package), aimed at large exports / batch cleanup / ETL — scenarios where `SelectList` could pull GBs into memory at once. **The implementation chose a single cursor over batched OFFSET paging**: OFFSET paging skips or duplicates rows without a stable sort (or when the table is written during iteration), and the framework cannot guarantee a stable sort key for the caller — that would push a silent bug onto the person least likely to inspect the data. A single cursor means exactly "the result set of this one SQL", introducing no second correctness condition at the framework layer. The cost is documented explicitly: the cursor holds a connection for the whole iteration; break / return closes the cursor and returns the connection immediately; writing to the same table mid-iteration depends on the dialect's isolation level, so wrap in a transaction for cross-dialect consistency. `Limit` / `OrderBy` / `GroupBy` / `Distinct` come from the supplied `q` with no second-guessing (iteration stops at LIMIT). Soft-delete semantics match `SelectList` exactly (`applyLogic`, `Unscoped` excepted); row mapping reuses `newRowScanner` (sharing the column-mapping plan with `SelectList`, so guards such as duplicate-name errors apply naturally). An empty result set yields 0 rows and no error; a mapping failure goes through the `(nil, err)` channel once and then terminates. `Repo[T]` wraps `QueryIter`. - **fix: `AutoMigrate` did not add missing columns to existing tables — new model fields were never created (P2)**: previously only `CREATE TABLE IF NOT EXISTS` ran, and once a table existed **the whole statement was skipped**, so "add a field to the model, re-deploy" made AutoMigrate return success without a word while the column did not exist — until some SELECT / INSERT hit it and failed at runtime with `no such column`, which looked like a bad query but was really a migration that never took effect. UNIQUE`, so all three dialects use `CREATE UNIQUE INDEX` (equivalent guarantee; different error wording and `ON CONFLICT` target name); ③ **indexes always run after column addition** — when the missing column carries `,index`, creating the index first hits "column does not exist", and that error is not swallowed by the "index already exists" idempotency path (measured: PG `column "score" does not exist`, MySQL `Error 1072`); ④ **metadata queries go to the primary** (new `queryPrimaryContext`) — it is a SELECT and would otherwise be routed to a replica whose DDL may lag, yielding conclusions opposite to reality. - **known limitation (unchanged, recorded)**: **a wrong or missing column name does not error on SQLite** — it falls back to treating an unparseable double-quoted identifier as a **string literal** (a well-known SQLite misfeature), so `WHERE "email" = ?` becomes `'email' = 'bob@x.com'` → always false → 0 rows, no error. ## v0.1.12 (2026-09-24)

- **fix: vector argument count did not match placeholder count (aggregate queries passed one extra argument, and MySQL's `Nearest` had never worked)**: `Build()` used to put the vector into `args[0]` **unconditionally** at the top, while three separate places render the distance expression, each with its own switch (the dist column in the projection governed by `noVecCol`, the threshold filter by `vecFilterOn`, and distance ordering skipped entirely for aggregates). Both directions broke: (1) calling `Count` / `Sum` / `Avg` after `Nearest(...)` — the RAG pattern "how many rows are in this vector's neighbourhood" — left only `COUNT(*)` in the projection with no placeholder at all while still carrying the vector, so `database/sql` compared the driver-reported `NumInput` in `driverArgsConnLocked` and failed with `sql: expected 0 arguments, got 1`; with a `WHERE` clause the arguments shifted wholesale (`SELECT COUNT(*) FROM "articles" WHERE "title" = $2`, the vector taking `$1`). (2) The same vector appearing twice was supplied once: PG's `$1` is **referential**, so the dist column and `ORDER BY` can share one parameter for free, but MySQL / SQLite's `?` is **positional** and needs one argument per occurrence — so `SELECT ..., VECTOR_DISTANCE(?, ...) AS dist ... ORDER BY VECTOR_DISTANCE(?, ...)` carried a single vector and failed with `sql: expected 2 arguments, got 1`, meaning **MySQL's `Nearest` had never worked** (SQLite has no native vector type and this path only generated SQL anyway, but its shape was wrong too). More importantly, a new `strictDriver` implements `NumInput` by real driver rules (positional dialects = the count of `?`, matching `go-sql-driver/mysql`'s `mysqlStmt.NumInput() → paramCount`; referential dialects = the highest `$n` ordinal), letting `database/sql` catch mismatches itself — the project's existing `ormmock` driver returned `-1` from `NumInput()` (effectively waiving validation), so this class of error was **completely invisible** on mocks, which is exactly how MySQL's vector path slipped through; `TestStrictMockEnforcesArgCount` proves in reverse that the driver really does reject, otherwise the green suite would only mean "no validation at all". - **feat: `OnlyColumns` write whitelist**: `UpdateById` / `Update` write **all** writable columns by default, so unassigned entity fields are written back too — the classic accident being `time.Time`'s zero value (measured in `bench/`: a payload omitting `created_at` wiped the row's timestamp to `0001-01-01` on every iteration). The new `OnlyColumns(cols ...string)` static whitelist complements `OmitZero`'s dynamic filtering and composes with it (whitelist first, then zero filtering). - **fix: `Count` dropped JOINs (total disagreed with the list)**: `Count` assembled `FROM` itself and omitted `JOIN` entirely — INNER JOIN changes row counts, so `Count` disagreed with `SelectList`'s real row count and `Page`'s page numbers / `HasNext` were wrong (fine in single-table tests, exposed only with joins in production). Unified into `Query.fromClause`, shared with aggregates; `Exists` was corrected at the same time.
- **fix: vector columns under aggregates / single-column projection**: aggregate and `Pluck` projections are fixed, so appending a vector distance column turned a 1-column result into 2 (`Scan` reporting `expected 1 destination arguments in Scan`), and "order by distance" in an aggregate query is invalid SQL on PG (the `ORDER BY` expression's column appears neither in the projection nor in `GROUP BY`). Both are now pruned per scenario.
- **fix: `Upsert` silently inserted on auto-increment primary keys (data-corruption level)**: running `Upsert(e, []string{"id"})` against an existing row **added a row** instead of updating the target — `writableCols` skips `autoInc` columns, so the INSERT had no `"id"`, `ON CONFLICT ("id")` / `ON DUPLICATE KEY` never matched, and the database assigned a new key and inserted normally, with no error. Measured on all three dialects against real databases; the existing mock tests `TestUpsertPG` / `TestUpsertMySQL` had frozen exactly that broken SQL as their "expected" value, which is why it stayed hidden. Added `upsertConflictCols`: when the conflict key is the auto-increment primary key and the entity carries a non-zero value, the column is added to the INSERT list (still omitted at zero, letting the database assign). The batch variant `upsertBatchConflictCols` is constrained by consistent multi-row VALUES column counts and decides per batch — when only some rows carry a key it **errors** rather than guessing.
- **feat: `Upsert` backfills auto-increment primary keys**: aligned with `Insert` — PG / SQLite use `INSERT ... ON CONFLICT ... RETURNING` (which returns the target row even on the `DO UPDATE` branch), and MySQL appends the official trick `` `id` = LAST_INSERT_ID(`id`) `` to `ON DUPLICATE KEY UPDATE` (on the update branch a bare `LAST_INSERT_ID()` does not point at that row). Both capabilities are detected via **optional interfaces** (`upsertReturningDialect` / `upsertPKCapturingDialect`), leaving the `Dialect` interface untouched so custom dialects need no changes. `BatchUpsert` still does not backfill, consistent with `BatchInsert`.
- **fix: MySQL does not support `CREATE INDEX IF NOT EXISTS`**: AutoMigrate emitted that clause unconditionally, and MySQL (including 8.x) rejects it with `Error 1064` (only MariaDB has `IF NOT EXISTS`). `createIndexSQL` now dispatches by dialect: MySQL gets a plain `CREATE INDEX`, with idempotency provided by `AutoMigrate` ignoring "index already exists" errors (`isDuplicateIndexErr`, matching MySQL 1061 and the PG/SQLite already-exists messages).
- **fix: SQLite's `JsonContains` generated a non-existent function**: SQLite's JSON1 extension has **no** `json_contains`, so the emitted `json_contains(col, ?)` failed at execution. It is now expanded with `json_each` into equivalent shallow "subset" semantics (every key/value pair of the candidate object is found in the column object with the same name, value and type), aligning with PG's `@>` and MySQL's `JSON_CONTAINS` (shallow only, not recursive).
- **fix: SQLite time-column aggregates could not be scanned back**: `MAX(col)` / `MIN(col)` are untyped expressions, so the modernc driver hands them back as TEXT (measured as Go's `time.Time.String()`, e.g. `2026-09-01 16:00:00 +0000 UTC`), and `sql.Null[time.Time]` fails to scan them; reading the same field from its declared column works fine. `MaxOf` / `MinOf`'s time branch now scans into `any` first, then normalises across dialect time-text formats.
- **test: real-database integration submodule `integration/`**: mocks only assert "which SQL string was generated" and cannot verify driver return types, dialect syntax legality, both primary-key backfill paths, or real transaction/lock/constraint behaviour. A nested module (importing drivers there so the main module stays dependency-free, following the `examples/` `replace => ..` convention) runs the same 24 cases against SQLite / PostgreSQL (pgvector) / MySQL, with a `docker-compose.yml` and a separate CI job; it is what surfaced and regression-tested the dialect issues above.
- **test: cross-framework benchmark submodule `bench/`**: using the same table, the same seed data, and semantically identical SQL, it compares `database/sql` (the lower bound) / GORM / this library on an in-memory SQLite database to strip out network factors. It covers 5 single-table scenarios plus a `BatchInsert` batch-size sweep, and carries a more important artefact: `TestResultParity` asserts all three layers **return identical data**, and `TestSQLParity` prints the SQL each layer **actually issues** (via a logging hook rather than DryRun, since the latter cannot reach fixed-template paths like `SelectById` / `Insert` / `UpdateById`); both run in CI to keep the benchmark from drifting away from the implementation. Measured results: `InsertOne` / `UpdateByID` are close to raw SQL (2.2× / 1.3× faster than GORM), `Count` matches raw SQL, and **`ListPage` is the one clearly slower read path** (26% slower than raw SQL for 50 rows, 2.4× the allocations — reflective row mapping is the hotspot); `BatchInsert` throughput peaks around chunk ≈ 10 rather than "bigger is better".
- **perf: row mapping moved from "once per row" to "once per query" (48% fewer allocations for `ListPage`)**: previously every scanned row called `rows.Columns()`, built two `map[string]*` (`idx` and `jsonCols` — the latter even for models with no JSON columns), and allocated two `[]any` buffers; all of that depends only on the **result-set column set**, not on any particular row, so every row of the same query repeated identical work. The "column signature" (FNV-1a hash, avoiding the string-concatenation key allocation) now caches "column order → field index + assignment function" on the model metadata (`modelMeta.scanPlanFor` / `scanPlan` / `rowScanner`), constructed once and reused per row by `SelectList` and the `Preload` list path; single-row paths (`SelectById` / `RawQuery`) are unchanged. `setField`'s per-type branches were extracted into standalone functions so the plan selects the assignment function at build time, dropping the per-row Kind switch. **Zero behaviour change**: scalar specialisation covers only string/integer/unsigned/float/bool, and everything else (structs, slices, maps, JSON columns) falls back to the generic implementation. Measured with a mock driver (no database engine) on 50 rows × 9 columns: `SelectList` 96,341 → 23,864 ns, 87,267 → 27,573 B, 498 → 101 allocs; the real-database `ListPage` dropped from 123,556 → 63,797 B and 2,304 → 1,906 allocs (within the same run all three layers' ns/op already sit inside the noise band). The plan cache is capped at 128 per model, degrading to "rebuild every time" (i.e. the previous cost) beyond that so dynamic column lists cannot blow it up.
- **test: regression cases for the row-mapping plan cache**: `TestScanPlanColumnSets` (the same model queried with all columns / reversed column order / a column subset / an unknown column / an empty result set — mapping must be correct in every case, because the plan is cached by column signature and a parsing mistake shows up as "the second query maps to the wrong fields", which a single-query case cannot detect), `TestScanPlanCacheCap` (511 column combinations beyond the cap must still be correct), and `TestScanPlanConcurrent` (concurrent queries sharing the cache); also added `BenchmarkScanList` / `BenchmarkScanListJSON`.

### Fixes (found in code review)

- **Vector serialization precision (`vector.go`)**: `formatFloatVal` promoted `float32` to `float64` and still formatted as 64-bit, so **fixed-size array** vectors (e.g. `[3]float32{0.1,1.5,2.2}`) serialized as `[0.10000000149011612,1.5,2.200000047683716]` while `[]float32` went through `floats32ToText` and correctly produced `[0.1,1.5,2.2]` — two containers with identical semantics writing different text, affecting vector column writes and distance computation. Each kind now formats with its own bitSize (32 / 64), giving identical results.
- **Column-name validation for map-based partial updates (`crud.go`)**: `UpdateSets` / `UpdateByIdSets` / `UpdatePartial` took plain string map keys and spliced them into the SET clause quoted, so a typo (e.g. `nmae`) could only be reported by the database, and external input (HTTP parameters, configuration) became an injection surface (`UPDATE t SET "name = 'x' OR 1=1 --" = $1`). New `checkSetCols` validates columns against the model metadata before building SQL, returning an error without issuing SQL; `Query.Set` (already constrained via `ColExpr`) is routed through the same check.
- **SQL legality of Offset without Limit (`query.go`)**: `Query.Offset(n)` alone generated `... OFFSET 20`, a syntax error on MySQL / SQLite. A LIMIT with no upper bound is now supplied per dialect — MySQL `LIMIT 18446744073709551615`, SQLite `LIMIT -1`; PostgreSQL's `OFFSET` works standalone and **rejects negative LIMIT** (`LIMIT must not be negative`), so nothing is added there (it cannot share SQLite's `LIMIT -1`). `Limit(0)` is not treated as "fetch 0 rows".
- **Non-deterministic column order in JSON sample inference (`gen/json.go`)**: `ParseJSONSample` ranged over the JSON object's map directly, so the same sample inferred fields in a different order every time (diff noise in generated output, randomly failing test assertions — actually reproduced in CI). It now infers after sorting keys, and `gen/json_test.go` asserts stability.
- **Regression tests (`fix_regression_test.go`)**: added `auditExecutor` (a lightweight executor that records issued SQL) plus three classes of assertion — `float32` array/slice serialization parity, unknown column names rejected without issuing SQL, and Offset-only SQL shape across three dialects (PG adds no LIMIT, SQLite adds `LIMIT -1`, MySQL adds an unbounded LIMIT).
